Apresentação do Projeto Integrador

CardápioHub 🍔🍕
SaaS Multi-tenant de Cardápio Digital, Pedidos e KDS

Demonstração prática e ao vivo do Núcleo Multi-tenant em execução: 2+ serviços rodando em contêineres, comunicação orientada a eventos e isolamento estrito de dados entre restaurantes concorrentes.

🏛️ Arquitetura Sólida

Persistência em Schema-per-tenant no PostgreSQL 16 (ADR-001) e isolamento de runtime em Fastify com injeção de search_path (ADR-004).

⚡ Comunicação Híbrida

Núcleo transacional síncrono (< 120 ms) e processamento pesado assíncrono via Redis 7 / BullMQ com idempotência estrita (ADR-002).

🟢 Pipeline Verde & CI

GitHub Actions automatizado validando compilação TypeScript, Dockerfiles e estrutura canônica docs/ a cada commit.

Visão do Produto & Personas de Tenant

O Problema do Food Service & Os Dois Tenants

Bares e pizzarias perdem de 12% a 27% do faturamento em taxas abusivas de marketplaces. O CardápioHub oferece autoatendimento web direto e KDS em tempo real para dois perfis de lojistas:

🥖 Tenant Pequeno (Interior) R$ 99,00 / mês
  • Estabelecimento: Lancheria Xis do Gaúcho (Horizontina - RS)
  • Volume Operacional: ~600 pedidos/mês (média de 20 pedidos/dia)
  • Usuários: 3 (1 caixa e 2 chapeiros na cozinha)
  • Restrição Chave: Custo unitário de infraestrutura marginal < R$ 3,00/mês. Banco dedicado (Silo) inviabilizaria o negócio.
🍕 Tenant Grande (Capital) R$ 899,00 / mês
  • Estabelecimento: Pizzaria Suprema Express (Porto Alegre - RS)
  • Volume Operacional: ~18.000 pedidos/mês (~600 pedidos/dia)
  • Horário de Pico: Sextas/Sábados com rajadas de 150 pedidos/hora
  • Usuários: 45 colaboradores (múltiplas telas KDS e caixas)
  • Restrição Chave: Throughput alto no KDS, rate-limiting anti-vizinho barulhento e zero risco de vazamento de dados.
Topologia dos 2+ Serviços

O Que Vamos Rodar: 4 Containers Integrados

Toda a stack da Etapa 2 roda localmente com paridade de produção via Docker Compose a custo R$ 0,00 (ADR-003):

Database
cardapiohub-postgres

PostgreSQL 16 Alpine com schema global public e schemas dinâmicos isolados por restaurante (tenant_xis_gaucho e tenant_suprema_express).

Message Broker
cardapiohub-redis

Redis 7 Alpine com persistência AOF para gerenciar filas BullMQ, pub/sub e travas atômicas de idempotência (SETNX).

Serviço 1 (HTTP/WS)
cardapiohub-api

Node.js 20 + Fastify (porta 3001). Autenticação, injeção de SET LOCAL search_path por transação e checkout com chave Pix.

Serviço 2 (Fila)
cardapiohub-worker

Node.js 20 + BullMQ. Drena a fila orders, processa status para EM_PREPARO e despacha WhatsApp assíncrono.

Ambiente & Build

Subindo o Ambiente Local via Terminal

Na raiz do projeto, executamos o comando de inicialização com compilação e build automáticos:

Terminal / Shell
$ docker compose up --build -d
📋 Orquestração de Containers:
  • Compila os códigos TypeScript tanto da API quanto do Worker via Dockerfile multi-stage.
  • Inicializa o PostgreSQL e executa o script DDL 01-init-schemas.sql provisionando os schemas dos 2 tenants.
  • Valida o healthcheck do Redis e Postgres antes de liberar a inicialização da API e do Worker.
  • Garante que nenhum serviço suba sem conectividade de dados.

Execução do script automatizado de validação de isolamento multi-tenant:

Terminal / Shell

Fechamento & Arguição

Conclusão da Defesa Técnica (Etapa 2)

Tudo o que a régua de avaliação da Etapa 2 exige está implementado, testado e documentado:

ADR-001: Tenancy

Schema-per-tenant no PostgreSQL. Viabiliza o plano de R$ 99 com custo marginal < R$ 3/mês e elimina o risco de queries SQL cruzadas.

ADR-002: Comunicação

Comunicação mista: Fastify síncrono para checkout e BullMQ/Redis assíncrono para I/O externo com idempotência em 3 níveis.

ADR-004: Runtime

Injeção dinâmica de SET LOCAL search_path na transação atômica. O pool de conexões é compartilhado e seguro.
